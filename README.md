## Problems I encountered
1. Handling difficult inputs including any form of quotes. 
One of the first larger problems I encountered was parsing more complex user input containing single quotes, double quotes, escaped characters and spaces.

My first implementation seperated only the command from the remaining input. This worked for simple commands but became difficult to extend once quoting had to be handled correctly.

I rethought my initial idea of reading user input by drawing my current system out on a blank sheet of paper. With this, I got a good overview of how I am currently reading in input and
how it would be better.

I changed reading user input character by character and storing the output in an 2D array is the best option. This made it possible to keep track of the current parsing state, such as whether the parser is inside single quotes, double quotes or normal input, while still producing tokens that can later be processed independently.

2. Building an interactive terminal
One I started implementing features such as command history, arrow-key nagivation and tab completion, normal line-based input was no longer sufficient.

Therefore, I changed the terminal into *non-canonical mode* using termios and disable the ECHO and ICANON flag. From this point on the shell became responsible for processing individual keystrokes and updating the terminal output itself using functions such as read() and write().

This also meant handling special input such as Backspace, Enter, Ctrl-D and multi-byte escape sequences, which are generated by the arrow keys.

3. File descriptors with multiple processes
For an input containing multiple commands connected through |, the shell has to create several processes and connect them using pipes. Drawing out the amount of processes I need for a specific user input and connecting them with pipes helped me visualize the data flow.

For n commands, the shell requires n processes and n - 1 communication pipes. The first process writes into a pipe, processes inbetween need to read _and_ write from the pipe while the last process has to read from the pipe and print the output to stdout.

The difficult part was not only creating the pipes, but managing their file descriptors correctly. Each child process must redirect the required descriptors using dup2() and close every pipe as soon as it dont needs it anymore. The parent process also has to close its file descriptors, otherwise one process might wait for EOF even though the process producing the data has already terminated.

Working through this improved my understanding of UNIX processes, pipes and files descriptor ownership.

4. Deciding where commands should execute
An important design question was, deciding whether a command should be executed in the shell process itself or inside a child process.

For external programs, creating a child process and replacing it using exec is the expected behavior. However, this does not work for every built in command.

For example, if cd is executed inside a child process, only the directory of that child changes. Once the child terminates, the parent process, the shell, is still in the original directory. Therefore, commands that are supposed to modify the state of the shell itself have to be executed directly in the parent process.

Pipelines make this problem more interesting, because a built in command may sometimes have to run inside a child process so that its input and output can be connected to the correct pipeline. Designing the execution logic therefore required considering both the type of the command and the context in which it is executed.


## AI Usage
Since AI can enhance the speed and quality, my workflow is as follows: First, I think about how I could implement the new feature: How could I design it such that it works well with the current implementation? What concepts do I need to build this feature? Can I reuse other functions? After I got a few ideas on how I could implement it, I will write it out, with this I get a clear mind and, moreover, find possible difficulties or things that would work well. I will give that text to an AI (usually GPT 6 Sol or similar) and ask it to give its opinion on what would make the most sense and which will give the best time/space complexity. Once I get the perspective of the AI, I will once again write it out so I can think about it. After all, I will implement it by myself. For these type of projects I dont use AI to write code, since I really want to learn and think about the implementation.
